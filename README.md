# Social Media Research Repository

This repository contains the code, processed data, and figures used for research on social media content, political bias, toxicity, topic classification, and consensus. The goal of sharing this repository is to make the research workflow more transparent and reproducible as I prepare the corresponding article for publication.

The project combines:

- Python-based data collection and processing
- Interactive analysis notebooks built with `marimo`
- Topic modeling and zero-shot topic classification
- An R script for mixed beta regression modeling
- A self-contained reviewer-response pipeline in `rebuttal/`

## Repository Overview

The repository is organized around a research pipeline that starts with post-level data collection and ends with statistical modeling.

It now holds two related bodies of work:

- The **original pipeline** that produced the submitted manuscript: `notebooks/`, `data/`, `figures/`.
- The **reviewer-response pipeline** under `rebuttal/`, which rebuilds the analytical sample from the same raw sources, verifies it against the submitted dataset row for row, and runs the additional analyses requested in review. See [Reviewer Response Pipeline](#reviewer-response-pipeline-rebuttal).

### Main folders

- `notebooks/`: Python `marimo` notebooks and the R modeling script.
- `data/`: input, intermediate, and final datasets used across the analysis.
- `data/zero_shot_results/`: outputs from topic classification models and manual evaluation data.
- `figures/`: exported figures generated by the R modeling script.
- `rebuttal/`: the reviewer-response pipeline — its scripts, its rebuilt dataset, its result tables and its figures, kept separate from the original analysis so neither overwrites the other.

### Main files

- `pyproject.toml`: Python project configuration and dependencies.
- `uv.lock`: locked Python dependency versions for reproducibility with `uv`.
- `README.md`: repository documentation.
- `PLOS_ONE_2026.pdf`: the submitted manuscript.
- `rebuttal/REVIEWER_RESPONSE.md`: the response to reviewers. Every number, table and figure in it is written by the scripts in `rebuttal/scripts/`.

## Research Workflow

At a high level, the workflow is:

1. Collect and process Facebook post data from MongoDB.
2. Match posts with link-level political bias metadata.
3. Extract news text associated with links.
4. Measure toxicity using the Perspective API.
5. Compute derived metrics such as reaction score and consensus index.
6. Add topic scores from zero-shot classification outputs.
7. Export the final analytical dataset.
8. Explore relationships in an interactive notebook.
9. Fit a mixed beta regression model in R.

## Files in `notebooks/`

### `notebooks/data_collection.py`

This is the main data preparation notebook. It is a `marimo` notebook stored as a Python file.

It includes several stages:

- Connects to a local MongoDB database (`crowd_tangle`) and reads Facebook post data.
- Joins post collections with political bias metadata from `data/links_rph_brazil.csv`.
- Removes duplicated posts and writes intermediate CSV files.
- Computes publisher-level political bias from post-level bias signals.
- Retrieves article text from URLs or joins previously saved text files.
- Calls the Perspective API to score toxicity-related attributes.
- Computes `reaction_score` and `consensus_index`.
- Joins zero-shot topic classification outputs.
- Filters and exports the final dataset to `data/data_final.csv`.

Important intermediate files used or generated by this notebook include:

- `data/links_rph_brazil.csv`
- `data/data_mongodb_duplicated.csv`
- `data/data_mongodb.csv`
- `data/urls_text.csv`
- `data/data_toxicity.csv`
- `data/zero_shot_results/resultado_zero_shot_MoritzLaurer_mDeBERTa-v3-base-xnli-multilingual-nli-2mil7.csv`
- `data/data_final.csv`

This notebook is the central preprocessing step for the rest of the repository.

### `notebooks/data_analysis.py`

This notebook is an interactive exploratory analysis environment built with `marimo`.

It reads `data/data_final.csv` and provides:

- Distribution plots for the main variables
- Political bias categorization for content and publishers
- Correlation heatmaps
- Boxplots and grouped comparisons
- Statistical testing helpers for comparing groups
- Threshold-based exploratory analysis for reaction count filtering

This file is best used for exploratory analysis, inspection, and figure development rather than for the core data-generation pipeline.

### `notebooks/topics.py`

This notebook focuses on topic analysis and topic classification.

Its main components are:

- Text preprocessing in Portuguese using `spaCy`
- LDA topic modeling with `gensim`
- Coherence-score comparison across topic counts
- Zero-shot classification using multiple transformer models
- Comparison of model outputs against manually labeled topic data

This notebook uses `data/data_final.csv` as input and also reads files from `data/zero_shot_results/` for validation and comparison.

### `notebooks/beta_model.R`

This R script fits the mixed beta regression model used in the final statistical analysis.

It:

- Reads `data/data_final.csv`
- Scales the main predictors
- Fits a beta mixed-effects model with `glmmTMB`
- Checks collinearity
- Produces a model summary table
- Extracts random effects for `account_name`
- Creates two figures:
  - `figures/correlation.png`
  - `figures/top_effects.png`

This script is the final modeling step in the repository.

## Running the Python Notebooks with `uv`

This project uses `uv` for Python dependency management.

### 1. Install `uv`

If you do not already have `uv`, install it following the official instructions:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

### 2. Sync the Python environment

From the repository root, run:

```bash
uv sync
```

This will create the virtual environment and install the dependencies declared in `pyproject.toml` and locked in `uv.lock`.

### 3. Open a `marimo` notebook

The Python notebooks in this repository are `marimo` notebooks saved as `.py` files. To open one interactively, run from the repository root:

```bash
uv run marimo edit notebooks/data_collection.py
```

You can do the same for the other notebooks:

```bash
uv run marimo edit notebooks/data_analysis.py
uv run marimo edit notebooks/topics.py
```

If you prefer read-only execution mode instead of editing mode, you can also use:

```bash
uv run marimo run notebooks/data_analysis.py
```

### 4. Environment and external services

Some parts of the workflow depend on local services or API keys:

- `notebooks/data_collection.py` expects a local MongoDB instance at `mongodb://localhost:27017/`.
- The same notebook expects the environment variable `PERSPECTIVE_API_KEY` for the Perspective API.

The project is configured to load environment variables from `.env` and `.env.testing` through `marimo`.

Example `.env` entry:

```env
PERSPECTIVE_API_KEY=your_key_here
```

### 5. Recommended execution order

If you want to reproduce the full pipeline, the recommended order is:

1. `notebooks/data_collection.py`
2. `notebooks/topics.py` 
3. `notebooks/data_analysis.py`
4. `notebooks/beta_model.R`

If `data/data_final.csv` is already available and you only want to inspect the results, you can start directly with:

- `notebooks/data_analysis.py`
- `notebooks/beta_model.R`

## Running the R Script

The repository also includes an R script for the final model.

### 1. Install the required R packages

Open R and install the required packages if needed:

```r
install.packages(c(
  "readr",
  "dplyr",

  "performance",
  "forcats",
  "ggplot2",
  "broom.mixed",
  "sjPlot",

  "car"

```

### 2. Run the script

Because the script uses relative paths such as `../data/data_final.csv`, the simplest option is to run it from inside the `notebooks/` directory:

```bash
cd notebooks
Rscript beta_model.R
```

This will fit the model and save the output figures to `../figures/`.

## Reviewer Response Pipeline (`rebuttal/`)

`rebuttal/` answers five requests raised in review. It is deliberately independent of `notebooks/`: it rebuilds the analytical sample from the raw sources (`data/data_mongodb.csv`, `data/urls_text.csv`, `data/data_toxicity.csv` and the zero-shot topic scores), checks the result against the submitted `data/data_final.csv` row for row, and only then runs the additional models. Nothing is copied from the earlier analysis, and nothing in `data/`, `figures/` or `notebooks/` is overwritten.

The written response is `rebuttal/REVIEWER_RESPONSE.md`; its Reproducibility appendix maps every claim to the file it comes from.

### Layout

- `rebuttal/scripts/`: the nine pipeline steps, plus `_common.R` (shared repository root, topic list, random-effect structure and final model formula) and `thresholds.txt` (the sharing-history ladder, read by both the R and the Python side).
- `rebuttal/data/`: the rebuilt `analysis_dataset.csv`, the rule-based `publisher_labels.csv`, and `post_timestamps.csv` with its own README.
- `rebuttal/results/`: every table and text output the document cites.
- `rebuttal/figures/`: the figures, as composites and as individual panels.

### Steps

| Step | Script | Output |
|---|---|---|
| 1 | `01_build_dataset.py` | `data/analysis_dataset.csv`, `results/build_log.txt` — the rebuilt sample and the full Table 1 ladder, including the reproduction check against `data/data_final.csv` |
| 2 | `02_publisher_labels.py` | `data/publisher_labels.csv` — rule-based ideological coding of the publisher frame |
| 3 | `03_descriptives.py` | `results/descriptives.txt` and the CSV tables behind Figures 1, 4 and 5 |
| 4 | `04_models.R` | `results/models.txt`, `model_coefficients.csv`, `model_fit.csv`, `model_vif.csv`, `model_random_effects.csv`, `model_marginal_effects.csv`, `published_table3_check.csv`, `models.rds` |
| 5 | `05_figures.R` | `figures/fig1*`–`fig6*` |
| 6 | `06_extract_timestamps.py` | `data/post_timestamps.csv` — a one-off recovery from the MongoDB snapshot; feeds nothing else |
| 7 | `07_bp_reliability.py` | `results/bp_reliability.txt`, `bp_reliability.csv`, `threshold_composition.csv` |
| 8 | `08_threshold_models.R` | `results/threshold_models.txt` and `.csv`, `figures/fig7*` |
| 9 | `09_negativity_outcome.R` | `results/negativity_models.txt` and `.csv`, `negativity_fit.csv`, `negativity_random_effects.csv`, `figures/fig8*` |

### Running it

Step 6 is omitted below: it needs the MongoDB snapshot and nothing downstream reads it. Run the rest in order, from the repository root, in the environment created by `uv sync`:

```bash
uv run python rebuttal/scripts/01_build_dataset.py
uv run python rebuttal/scripts/02_publisher_labels.py
uv run python rebuttal/scripts/03_descriptives.py
Rscript rebuttal/scripts/04_models.R
Rscript rebuttal/scripts/05_figures.R
uv run python rebuttal/scripts/07_bp_reliability.py
Rscript rebuttal/scripts/08_threshold_models.R
Rscript rebuttal/scripts/09_negativity_outcome.R
```

The R side needs:

```r
install.packages(c(
  "readr",
  "dplyr",
  "tidyr",
  "ggplot2",
  "forcats",
  "scales",
  "patchwork",
  "glmmTMB",
  "performance",
  "broom.mixed"
))
```

Every script — Python and R alike — locates the repository from its own path, so the working directory does not matter. Set `PROJECT_ROOT` to override that, for example when the scripts are copied elsewhere; a value that is not a repository root fails immediately rather than reading the wrong tree:

```bash
PROJECT_ROOT=/path/to/facebook_political_bias_study Rscript rebuttal/scripts/04_models.R
```

## Reproducibility Notes

- Python dependencies are managed with `uv` and pinned in `uv.lock`.
- The workflow mixes automated processing with files that may reflect prior scraping, API calls, or model outputs.
- Some steps depend on external services such as MongoDB and the Perspective API.
- Topic classification outputs in `data/zero_shot_results/` are included to support reproducibility without rerunning every heavy model step.
- The `rebuttal/` pipeline is deterministic: ties in every ranking are broken explicitly and the one figure that jitters points is seeded, so re-running it reproduces the committed artefacts byte for byte rather than merely to within a reshuffle.
- Steps 4, 8 and 9 of that pipeline derive the model from the single `FINAL` definition in `rebuttal/scripts/_common.R` rather than restating it, so they cannot drift into fitting different models.
